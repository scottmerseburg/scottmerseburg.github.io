Vertex Animation Shader

Overview and introduction

Overview

This project explores procedural animation for a small robot built in Unity using Shader Graph and C#. The goal was to create expressive movement and readable state-based behavior without relying on a traditional rig or animation clips. Instead, the robot is driven by shader-controlled vertex motion and gameplay signals coming from code.

Main components

The final setup is built from several technical parts working together.

  • Vertex Color Masks — Used to separate different parts of the robot mesh.
  • Shader Graph Animation — Controls shell turning, wheel motion, and antenna movement.
  • Procedural Motion — Movement is generated through signals instead of baked animation clips.
  • C# Control Signals — Handles movement, turning, wheel phase, alert states, and scan timing.
  • Material Property Blocks — Used to send dynamic values from code into the shader.
  • State-Based Behavior — Patrol, scan, and chase affect both motion and visuals.
  • Emissive Feedback — Color and intensity shift depending on the current robot state.

Behavior setup

The robot uses simple AI-driven states to make the movement feel more alive. The shader handles the visual deformation, while C# provides stable values for movement, turning, and state logic. This separation made it easier to control both the look and the behavior of the robot in a clean way.

  • Patrol — The robot moves between points with readable procedural motion.
  • Scan — The robot pauses, rotates, and feels more alert while checking its surroundings.
  • Chase — The robot becomes more direct and aggressive, with clearer emissive feedback.

Breakdown

A breakdown of the main technical parts used to build the procedural robot animation system.

Mesh masks

Vertex color channels were used to isolate different areas of the robot mesh. This made it possible to control separate parts of the same mesh independently inside Shader Graph without needing multiple skinned meshes or bones.

  • R — Outer shell / eye housing
  • G — One inner wheel
  • B — The other inner wheel
  • Combined channels — Used for inner core logic and extra motion control

Shader-driven motion

The main animation is done directly in Shader Graph. Different mesh parts are rotated around custom pivots using shader logic such as Rotate About Axis. Instead of one fixed animation, the robot responds dynamically to movement and state values sent in from code.

  • Shell rotation — Used for turning and directional feedback
  • Wheel rotation — Driven procedurally based on movement values
  • Inner core motion — Adds secondary motion and detail
  • Antenna animation — Uses bend and spring-like motion for extra character

Behavior signals from C#

C# was used to calculate stable inputs and pass them into the shader through Material Property Blocks. This helped separate gameplay logic from visual animation and made the system more reliable than trying to calculate everything directly in the shader.

  • MoveAmount — Controls movement intensity
  • TurnAmount — Controls turning direction and strength
  • Alert — A value for awareness and state feedback
  • Wheel phase — Integrated in code for stable procedural wheel motion
  • State weights — Blend values between patrol, scan, and chase

Behavior states

The robot uses a few simple states to make it feel more alive and readable. These states affect both the movement pattern and the shader response, which gives the robot a stronger sense of awareness and intention.

  • Patrol — Calm navigation between patrol points
  • Scan — Idle state with extra motion and environmental awareness
  • Chase — Faster and more focused movement with stronger visual feedback

Emissive state feedback

Emissive values were used to help communicate the robot’s current state. By blending between different intensities and colors, the same robot can feel calm, alert, or aggressive depending on what it is doing.

This was an important part of making the system feel reactive, since it added readable feedback without needing extra animations or UI elements.

Challenges

  • One of the biggest challenges was getting stable wheel motion. Early versions calculated too much directly in the shader, which caused flickering and snapping.
  • Another challenge was blending turn and movement behavior in a way that felt smooth and readable without making the robot feel too mechanical or too unstable.
  • It also took time to find a good balance between AI behavior and procedural animation, especially for the scan state and how often it should trigger.
  • A large part of the work was making sure the same system could feel expressive while still staying technically simple and controllable.

If I had more time

  • I would like to polish the transitions between patrol, scan, and chase even more so the robot feels smoother and more natural.
  • I would also like to expand the visual feedback further, for example with more detailed emissive changes or additional reactive motion in the shader.
  • Another thing I would like to continue exploring is adding more procedural secondary motion to strengthen the character of the robot even further.
